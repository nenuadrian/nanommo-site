    About

    nanoMMO is a devlog where I build an MMO from scratch in C++, with features I'd like to see exist, even if some might be impractical for most games, such as players creating their own skills. It's a learning journey, with the software engineering and the hard parts out in the open, and not always about the gameplay.

    We build both the client and the server, and quite a bit of the time goes into the engineering around them: Docker and deployment, CI, benchmarking, Prometheus and Grafana, MySQL and Redis, networking, security, testing and profiling. These are the parts that decide whether a game server holds up once players arrive, and they're the parts tutorials tend to skip. What broke along the way, and what was hard to get right, is gathered on the hard parts, each with the episode it's in.

    Where it's going

    A disclaimer first: it might not scale in the end, for one reason or another.

    What interests me is dynamic intelligence, and a world that evolves. I'd like to end up with something like Sword Art Online, in the sense of a world that can adapt of its own volition. Later on, perhaps, an AI agent could generate quests on the fly, made for a specific player, and items too. And there are features I'd like to see exist even if they're impractical for most games, such as a system for players to create their own skills.

    The first small step is already there. In episode 25, a storyteller NPC writes you a story from a few words, with mvGPT, the small GPT from my other series, served next to the game.

    Who it's for

    It's for anyone curious about how the pieces of an online service fit together, from one end to the other, in a codebase small enough to read. You don't need to have made a game before, or to write software for a living. Some C++ helps, and every change is typed out on screen, with the reasons behind it.

    The code

    The game's code is on GitHub, under the MIT licence. Every step of every episode is a tag in the repository, so you can check out the code at any point in a video, build it and run it yourself. Each episode's page lists its steps, with links to browse the code at each one and to see what changed since the step before. Why the game is built the way it is, and what we weighed and turned down, is written up in its decision records.

    Reading around it

    Two books go well with the series. Design Patterns, by Gamma, Helm, Johnson and Vlissides, the Gang of Four, is the one that gave names to patterns like Observer, Command and State. Robert Nystrom's Game Programming Patterns goes back over them as they turn up in games, adds the ones games need, like the game loop, and is free to read online.
